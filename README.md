# Spec-driven development: a worked example

A small, self-contained example of how I work as a product owner when coding agents do part of the build: the **spec is the source of truth**, written as Markdown in the repo, and the code is implemented from it.

> Everything here is fictional. "Nimbus" is an invented B2B marketplace where resellers buy cloud subscriptions from vendors. No real company, customer or vendor data is used.

## What's in here

| Path | What it is | Who it's for |
|---|---|---|
| `AGENTS.md` | Project context and rules for coding agents | Agents (and new engineers) |
| `specs/constitution.md` | Non-negotiable product and engineering principles | Everyone |
| `specs/001-seat-change-proration/requirements.md` | What to build: user stories and testable acceptance criteria (EARS) | Product, engineering, QA, agents |
| `specs/001-seat-change-proration/design.md` | How it's built: data model, calculation, decisions and trade-offs | Engineering, agents |
| `specs/001-seat-change-proration/tasks.md` | Ordered, independently testable tasks, each traced to requirements | Agents, engineering |
| `src/`, `tests/` | The implementation and tests built from the spec | - |

## The feature

A reseller changes the number of seats on a monthly subscription in the middle of a billing cycle. Sounds simple; it is where billing errors and revenue leakage usually come from: proration, rounding, vendor-specific rules for decreases, minimum seat counts, and retries that charge twice.

## How the workflow runs

1. **Constitution** - principles that every feature must respect (money is never a float, every rule has a test, ...).
2. **Requirements** - I write the behaviour as EARS statements. Each one has an ID and is testable on its own. Open questions are resolved here, not in code review.
3. **Design** - the technical approach, reviewed with engineering. Decisions are recorded with the alternative that was rejected and why.
4. **Tasks** - small steps in dependency order. Each task lists the requirement IDs it covers.
5. **Implement** - a coding agent works through `tasks.md`. Every test names the requirement it verifies.
6. **Converge** - if behaviour needs to change, the spec changes first, then the code.

## Traceability

Every requirement ID in `requirements.md` appears in at least one test name or docstring. `tests/test_traceability.py` fails the build if a requirement has no test.

## Run it

```bash
python -m pytest
```

Python 3.10+, no dependencies beyond `pytest`.

## How this was made

The specs were drafted with AI assistance and reviewed and edited by me. The implementation and tests were generated by an AI coding agent from the specs. That is the point of the example.
